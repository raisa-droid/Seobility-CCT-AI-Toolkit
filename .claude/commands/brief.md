# Brief Command

Invoke with: `/brief [paste brief feed]`

Generates a full content brief for a chosen H1 candidate. Input is a brief feed — a paste of outputs from upstream skills (Sera, DataforSEO) or manually supplied data. The brief is Draftwell-ready and can also be used to brief freelance writers directly.

## Dependencies
- `scripts/brief_dataforseo_paa.sh` — PAA fetch (Step 1a)
- `scripts/brief_gemini.sh` — Gemini research (Step 1b)
- `scripts/brief_dataforseo.sh` — KW overview / SV validation (Step 1f)
- `scripts/brief_reddit_miner.sh` — Reddit miner (Step 1e)
- `skills/golden-entity-map.md` — entity fetcher, run inline (Step 1c)
- `product-context/` — brand and product reference files (Steps 2a, 3)
- Google Drive MCP — Sitemap Cache GSheet for internal links (Step 2b)
- Notion MCP — Content Library for cluster state (if needed)

All scripts require `.env` in repo root with `DATAFORSEO_LOGIN`, `DATAFORSEO_PASSWORD`, and `GEMINI_API_KEY`.

# Seobility's Brief Skill

## Purpose

Generate a full content brief for a single chosen H1 candidate. Input comes from a brief feed — a paste of outputs from upstream skills (Sera, DataforSEO, SERP lookup, internal link recommender) or manually supplied data. The brief is Draftwell-ready and can also be used to brief freelance writers directly.

---

## Required inputs

The skill accepts a loose or structured paste. It looks for the following fields and extracts what it can. Missing fields are flagged after parsing — blocking fields stop execution, non-blocking fields get placeholders.

**Blocking (skill cannot proceed without these):**

- `Brand` — which brand this brief is for (e.g. Seobility)
- `H1` — the chosen H1 candidate
- `Seed KW` — the seed keyword
- `Primary KW` — the primary keyword
- `Funnel` — Top / Middle / Bottom
- `Topic summary` — a description of the angle, who it targets, how the brand enters, and why it's worth writing. Can come from Sera's output explanation or be supplied manually.

**Non-blocking (skill proceeds with placeholder if missing):**

- `Contextual KWs` — generated by the skill in Step 1f if not supplied
- `Entities` — generated by the skill via entity fetcher in Step 1c if not supplied
- `Internal link candidates` — generated by the skill in Step 2b if not supplied
- `External references` — optional; supplied by the user only. If not supplied, section is omitted.

If any blocking field is missing, stop and ask for it before proceeding. Do not infer blocking fields from context.

---

## Parsing behaviour

The skill reads whatever is pasted and maps content to the fields above. It does not require a specific format. After parsing, it outputs a brief confirmation block before generating the brief:

```
Parsed fields:
- Brand: [value]
- H1: [value]
- Seed KW: [value]
- Primary KW: [value]
- Funnel: [value]
- Topic summary: [confirmed]
- Contextual KWs: [value or MISSING — will generate]
- Entities: [value or MISSING — will generate via entity fetcher]
- Internal links: [value or MISSING — will generate from sitemap]
- External references: [value or MISSING — will omit section]

Proceeding to generate brief.
```

Do not ask for confirmation after the parsing block — proceed immediately.

## Step 1 — Research, entity mapping, and selection

The H1 is the anchor for all research — not the Primary KW.

### 1a — SERP research (web_search + web_fetch) and PAA (DataforSEO)

Run both of the following in parallel:

**Organic SERP research:**
1. Run `web_search` using the H1 as the query
2. Take the top 3 organic URLs from the results
3. Run `web_fetch` on each URL — read page content: H2s, key concepts, terminology, named concepts and entities
4. While fetching, identify and record:
   - **Dominant SERP format** — the content format that appears most frequently across the top 3 results (e.g. listicle, how-to guide, comparison, pillar page, definition piece)
   - **Search intent** — the dominant intent type (Informational, Commercial, Navigational, Transactional)
   - **Average word count** — approximate content length of the top 3 results, used to generate a word count benchmark

**PAA fetch (DataforSEO), with related_searches fallback:**
1. Run `brief_dataforseo_paa.sh` via bash with the H1 as the input: `./scripts/brief_dataforseo_paa.sh "[H1]"`
2. Read `paa_present`, `questions`, and `related_searches` from the JSON response
3. If `paa_present: true` — apply the same fit filter used for the `related_searches` fallback below before storing the list for use in Step 3 (FAQs H2). Native PAA questions are not guaranteed to be on-topic just because Google surfaced them — off-topic or format-mismatched questions (e.g. "Is SEO dead now with AI?" or "What is the 80/20 rule in SEO?" surfacing for an H1 about SEO timelines) must be dropped the same way a bad `related_searches` item would be:
   - **Filter for fit** — drop any item that: duplicates territory already owned by a different-funnel companion piece in the same seed KW cluster; belongs to a different seed KW cluster or topic entirely; or points to a different content format than this H1 (a template, download, or tool-homepage query rather than something answerable in 2–3 sentences).
   - **Cross-check survivors against existing H2/H3 headings** already drafted in the Structure section — drop anything that just restates a step or section.
   - **Merge near-duplicates** — PAA can surface the same underlying question in different phrasings; collapse to one representative version.
   - PAA questions already arrive question-shaped — no rephrasing needed, unlike the `related_searches` fallback.
   - **Cap at 3–5** per the standard FAQ count — a final trim, not the primary filter.
   - If zero items survive filtering, no FAQs H2 in the brief — this is a valid result, not an error. Do not fall back to `related_searches` in this case; it is empty when `paa_present: true`.
4. If `paa_present: false` — fall back to `related_searches` (already deduped and stripped of query-echo artifacts by the script):
   - **Filter for fit** — drop any item that: duplicates territory already owned by a different-funnel companion piece in the same seed KW cluster (e.g. a "what is X" phrase when this H1 isn't the Top piece); belongs to a different seed KW cluster entirely (e.g. a "local" variant when this H1's cluster isn't local); or points to a different content format than this H1 (a template, download, or tool-homepage query rather than something answerable in 2–3 sentences).
   - **Cross-check survivors against existing H2/H3 headings** already drafted in the Structure section — drop anything that just restates a step or section (same duplicate check applied to PAA-sourced questions).
   - **Merge near-duplicates** — collapse variants of the same underlying question into one representative version rather than listing each phrasing separately.
   - **Rephrase into questions** — `related_searches` arrives as bare keyword phrases, not questions. Convert each survivor into a natural question a reader would actually ask.
   - **Cap at 3–5** per the standard FAQ count — but only as a final trim; filtering for fit should usually do most of the narrowing on its own. If filtering leaves fewer than 3, use what survives rather than forcing the count.
   - If zero items survive filtering, no FAQs H2 in the brief — same as a native `paa_present: false` with no fallback data. This is a valid result, not an error.
5. If `data_available: false` — log the error, proceed with no FAQs section.

### 1b — Gemini research (bash)

1. Run `brief_gemini.sh` via bash with the H1 as the input: `./scripts/brief_gemini.sh "[H1]"`
2. Response returns `synthesis` (Gemini's full generated text) and `sources_raw` (source section as raw text)
3. Extract URLs from `sources_raw` — skip any URL that is a root domain, homepage, tool homepage, documentation index, or `vertexaisearch.cloud.google.com` redirect. Only extract URLs pointing to a specific article or page.
4. If 1 or more valid article URLs remain after filtering, run `web_fetch` on up to 3. If no valid URLs remain, skip web_fetch entirely and proceed with the Gemini synthesis text only.
5. Use both the Gemini synthesis text and any fetched page content as research inputs.

If the script returns `data_available: false`, log the error, skip 1b, and continue with 1a results only.

### 1c — Entity fetcher (Golden Entity Map)

Run the Golden Entity Map skill inline — no external call, no bash script. Execute the skill logic directly using the H1 and brand as inputs. The skill produces a strict JSON object with three arrays: `must_include`, `novel_information_gain`, and `must_avoid`.

**Before running, confirm the dominant SERP format from Step 1a.** This determines which entity rules apply:
- If format is listicle or comparison: third-party tool names, analytics vendors, and branded platforms are valid entities — the standard exclusion rule does not apply.
- All other formats: entities are named concepts, methodologies, standards, technical terms, and non-competitive organisations central to the topic. Descriptive or adjective-like terms belong in contextual KWs, not entities.

**Running the skill inline:**
1. Read `skills/golden-entity-map.md` for the full skill logic
2. Use the H1 as the target topic and the brand (e.g. Seobility) as the target website/brand
3. Conduct research using web_search as specified in the Golden Entity Map skill (Steps 2–3)
4. Generate the JSON output internally — do not surface the raw JSON to the user
5. Parse the three arrays immediately upon generation

**Using the JSON output — do not surface this processing logic to the user:**

- **`must_include`** → primary source for entities and contextual KW candidates. `semantic_weight` determines entity ordering. `context` values are used as writer direction in the Structure section — translated into instructions, never copied verbatim.
- **`novel_information_gain`** → held for Step 1d. Do not embed yet.
- **`must_avoid`** → loaded as a silent structural guardrail. Never mentioned in output. Used during Step 3 to eliminate any H2, H3, framing, or narrative direction that would cause topical drift. If a structural element conflicts with a `must_avoid` item, drop it without flagging it.

### 1d — Novel Info Gain selection

Take the `novel_information_gain` array from the Step 1c JSON and render it as a human-readable table. Do not surface the `must_include` or `must_avoid` arrays. Present to the user in this format:

```
Novel Information Gain options — choose which to include in the brief:

| # | Angle | Why it matters |
|---|-------|----------------|
| 1 | [entity value] | [context value] |
| 2 | [entity value] | [context value] |
...

Which of these would you like to add? You can select all, some, or none.
```

Wait for the user's response before proceeding.

**Handling selected angles:**
- Each selected angle gets a structural home in the brief — either a new H3 inside the most relevant existing H2, or a standalone H2 if the angle is substantial enough to stand alone or has no natural home in the existing structure.
- The decision between H2 and H3 is a judgment call: if the angle introduces a distinct audit component, scenario, or concept the reader needs to understand independently → H2. If it adds depth to a concept already covered under an existing H2 → H3.
- The entity fetcher Note for the selected angle drives what the section must cover — use it as the basis for writer direction in the Structure section, translated into instructions.
- The concept label used in the brief (in entities and Structure) is derived from the angle's meaning, not its NIG label verbatim. Example: "GBP Category Strategy as an Audit Variable" → entity label "GBP category selection", Structure direction covers category drift and competitor category mapping as a recurring audit checkpoint.
- Selected angles are added to the entity list for their respective Structure section.
- Unselected angles are dropped entirely.

If the user selects none, proceed without NIG additions.

### 1e — Reddit miner (brief_reddit_miner.sh)

1. Run `brief_reddit_miner.sh` via bash with the H1 as the input: `./scripts/brief_reddit_miner.sh "[H1]"`
2. The script returns a formatted block containing two sections: `Real scenarios & examples` and `Gaps worth addressing`
3. Parse the output — split at section headers:
   - Store `Real scenarios & examples` bullets silently — these will populate the Real-world context section in Step 3. Do not surface to the user. Once the Structure section is built, tag each stored scenario with the H2 it's most relevant to (see Step 3 output format) — do not leave scenarios unattached to a section.
   - Extract `Gaps worth addressing` bullets and present to the user for selection. Format:

```
Reddit gaps — choose which to carry into the brief:

[Gaps worth addressing bullets from miner output]

Which of these gaps do you want to include? You can select all, some, or none.
```

4. Wait for the user's response before proceeding.
5. Selected gaps feed into structure judgment in Step 3 alongside Must Include, selected NIG, SERP patterns, and reader/funnel logic. Each selected gap gets a structural home — H2, H3, or FAQ entry — based on content and what is already present in the structure.
6. If the script returns an error or no relevant threads were found, log it and proceed without Reddit findings. Real-world context section is omitted from the brief.

### 1f — SV validation (bash)

1. Run `brief_dataforseo.sh` via bash with Must Include terms (and any additional contextual KW candidates identified from Steps 1a/1b) as arguments: `./scripts/brief_dataforseo.sh "kw1" "kw2" "kw3"` — maximum 15 items
2. Response returns SV and intent per keyword
3. Apply SV ≥ 500 as a soft filter — preferred, not a hard drop. A term below SV 500 is retained if it meets any one of:
   - (a) it appears in 2+ sources from Steps 1a/1b
   - (b) it directly names an audit component, product feature, or reader task central to the H1
   - (c) it has no high-SV synonym already covering it in the candidate pool
4. Select 3–5 final contextual KWs from the validated list

If the script returns `data_available: false`, flag SV as unavailable and proceed with Must Include terms filtered by topic, product, and reader relevance only.

## Step 3 — Generate the brief

Produce the brief in the following format. Do not add sections. Do not remove sections. Follow field rules exactly.

Before generating, apply Must Avoid silently: review every planned H2, H3, framing note, and narrative direction against the Must Avoid table. Drop any element that conflicts with a Must Avoid item — no flag, no mention to the user.

**Output format:** Deliver the brief inline in chat as readable text (markdown rendered in Claude Code).

- **Meta title:** [H1 verbatim. No truncation or rewrite.]
- **Meta description:** [value. Primary KW front-loaded when possible. CTA-oriented. Max 160 characters. No em dashes.]

**URL slug:** https://www.seobility.net/en/blog/[generated-slug]

**Keywords**

Seed KW: [value]
Primary KW: [value]

Secondary KWs:
- [kw]
- [kw]

Contextual KWs:
- [kw]
- [kw]
- [kw]

**Word count:** [range, e.g. 1,800–2,400 words] *(Use as a guide, not a hard target)*

**Reader**

[1–2 sentences. Who lands on this page, what they already know, what they need to leave with. Source: Topic summary + Seobility ICP data from project files. Do not copy the topic summary verbatim — synthesise.]

**Core idea**

[1 tight paragraph. What the piece argues, why the angle works for the brand, and how it connects to the reader's need. Source: Topic summary + SERP pattern from Step 1 research + brand positioning from project files. Never lifted from the topic summary verbatim — always skill-generated.]

**Structure (Suggested H2 Skeleton. Optimize each H2/H3 copy for SEO/AEO.)**

[H2/H3 skeleton. Each heading is prefixed with its level tag. Format:

H2 — [Section title]
[1–3 sentences or short bullet list of writer direction for this section. Where a Must Include entity maps to this section, translate its Note into a direct writer instruction — do not copy the Note verbatim. Where a selected NIG angle maps to this section, translate its description into writer direction for what the section must explore. Where a selected Reddit gap maps to this section, translate it into writer direction for what the section must answer or resolve.]

*Entities: [entity name, entity name, entity name]* ← italicised, inline under the section direction. Branded names and tool names used as-is. Conceptual entities expressed as the concept they describe, not the NIG/Must Include label. Only entities that belong to this specific section appear here — no cross-section duplication.

H3 — [Sub-section title]
[Writer direction for this sub-section.]

*Entities: [entity name]* ← only if entity is specific to this H3 rather than the parent H2.

---

Entity placement rules:
- Every entity from Must Include and every selected NIG angle is assigned to exactly one section — the section where it is most central to the content.
- Entities shared across multiple sections still appear in only one section's entity list — the most relevant one.
- If an entity is broad enough to apply to the whole piece rather than a specific section, place it under the first H2 where it naturally appears.
- Branded names (e.g. Google Search Console, BrightLocal) → use as-is.
- Conceptual entities (e.g. "AI Search Visibility as an Audit Signal") → use the concept it describes (e.g. "AI search visibility") and ensure the Note informs the writer direction for that section, not just the label.

---

For tool listicles and comparisons: include an AEO comparison table as a standard structural element. Place it after the individual tool entries and before the closing section. Label it:

H2 — Comparison table

Note in direction: "AEO asset — structure for featured snippet and AI-generated answer extraction. First-person tested perspectives remain primary; this table supports them." Columns: Tool, Best for, Key features (3 max), Free plan / trial, Paid pricing (starting), SMB verdict (1 line).

**E-E-A-T instruction (listicles only):** When the dominant SERP format identified in Step 1a is a listicle, include the following note once, directly under the listicle H2, in italic, before the first H3:

*Writer note: Write this section as evaluated, not aggregated. Use language that signals first-hand experience throughout — e.g. "we reviewed", "we evaluated", "our take", "based on our analysis", "what we found", "our verdict". Avoid neutral roundup phrasing like "this tool offers" or "users can". The goal is copy that reads like it could only have come from Seobility's team.*

Do not repeat this note per H3 entry.

**FAQs:** Include a FAQs H2 as a standard structural element when either source below yields at least one usable question. It is always the final H2 in the Structure section, placed immediately before the closing/CTA section. Label it:

H2 — FAQs (Answer in 2–3 sentences. Write for AI extraction — clear, direct, no preamble.)

**Source priority:**
- If Step 1a PAA fetch returns `paa_present: true`: populate with the fit-filtered, deduped questions carried over from Step 1a, item 3 (up to 3–5). These arrive already question-shaped — no rephrasing needed. If filtering left zero usable items, omit the FAQs H2 entirely.
- If `paa_present: false`: populate with the filtered, rephrased, deduped questions carried over from the `related_searches` fallback (Step 1a, item 4). If that fallback yielded zero usable items, omit the FAQs H2 entirely.

Before populating from either source, cross-check all candidate questions against H2/H3 headings already present in the Structure section — drop any question that duplicates an existing heading. List questions as H3s only — no per-question answer direction. The answer direction appears once on the H2 label and applies to all H3s beneath it.

**Real-world context from Reddit**

[Only present if Step 1e Reddit miner returned scenarios. Populate with the `Real scenarios & examples` bullets from the miner output, verbatim — no rewriting, no synthesis. Each bullet keeps its source URL and gets one added tag pointing to the H2 it's most relevant to, in this exact shape:

- [scenario text, verbatim] → [source URL] *(recommend using in: [H2 title])*

The tag is a placement suggestion for the writer, not a rewrite of the scenario — the underlying text and URL must stay exactly as the miner returned them. If no single H2 is a clean fit for a scenario, tag it against the closest one rather than dropping the tag. If the miner returned no results or errored, omit this section entirely.]

**Flags & editorial notes**

[Always present. Use bullet points. Include any of the following that apply:

- **Cannibalization risk:** [conflicting URL] — [note on how writer should scope or differentiate to avoid direct conflict]
- **Framing:** [angle constraints, what to avoid, how to position the brand]
- **Format:** [format-specific instructions, e.g. checklist format only, required table, etc.]

If nothing applies, write: No flags.

Note: Must Avoid items are not listed here. They are applied silently during structure generation.]

**Internal links**

[Content-to-content links only. Generated from sitemap in Step 2b. Full URLs — no placement notes. Placement context is in the Structure section above. If sitemap fetch failed or no relevant URLs were found: Internal links: not available — add manually or run internal link recommender.]

**CTA:** https://www.seobility.net/en/pricing/

**External references**

[Only present if supplied by the user in the brief feed. Do not generate. If supplied, output as-is. If not supplied, omit this section entirely.]
